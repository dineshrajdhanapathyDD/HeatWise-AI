## Decisions (made here, from the code read)

- D-M5-1 Evaluation weather is a `ScenarioWeatherProvider` that serves synthetic fixtures stored in the dataset JSON (provider name `HeatWise evaluation fixtures (synthetic)`, `source_url="synthetic://heatwise/evaluation"`, `data_mode="demo"`). Both modes use it, so weather extraction has exact ground truth and no run touches the network for weather. It can inject `missing` fields, an old `observed_at` (staleness computed with `backend.services.weather.base.is_stale` and `settings.weather_stale_after_minutes`), and errors per call (`ProviderUnavailableError`, `ProviderTimeoutError`, `LocationNotFoundError`). Geocoding matches the first comma part, casefolded (like `tests/fakes.FakeProvider`), so a model that appends ", India" still resolves.
- D-M5-2 Offline mode uses the shipped `build_offline_coordinator` scripts unchanged (it gains only a `provider=` keyword). Offline numbers therefore measure the real offline pipeline, including steering blocks and deterministic fallback, not a script tailored to each scenario.
- D-M5-3 Live mode uses `HeatWiseCoordinator(settings, weather_agent=WeatherIntelligenceAgent(settings, provider=scenario_provider, model=metered), model=metered)`, where `MeteredBedrockModel` subclasses `strands.models.BedrockModel` and sums `metadata.usage` input/output tokens from `stream` events. Token counts are recorded; a dollar cost is computed only from a price fetched in this session from an official AWS page, else the report says "price not verified" and gives tokens only.
- D-M5-4 Expected risk categories are derived by hand from design.md §8.2 and stored per scenario with a `derivation` object (heat index °F, NWS band score, IMD indication score, indicator count, heuristic step). Values sit at least 1 °F / 0.5 °C away from every band edge. A dataset test recomputes them with an independent re-typed implementation of the §8.2 tables (only the WPC heat-index equation is reused from `risk_rules.heat_index_f`). Limitation stated in the report: agreement measures that the multi-agent pipeline carries the documented rule output into the report; it is not clinical validation.
- D-M5-5 Delegation order is a deterministic check over `report.trace` (no LLM judge): the successful `agent="coordinator"` and `agent="coordinator_fallback"` delegation entries in `step_index` order must equal the expected path for the scenario's expected status. Two metrics: effective order correct (fallback allowed) and model-driven order (no fallback steps and no steering blocks).
- D-M5-6 `strands-agents-evals==1.8.0` (dry run: installs only rich 15.0.0, markdown-it-py 4.2.0, mdurl 0.1.2, tenacity 9.2.1; strands-agents stays 1.63.0) goes into the `dev` extra and a new `eval` extra, never into `infrastructure/lambda-requirements.txt`. It is used for the live LLM-as-judge (`OutputEvaluator` through `Case`/`Experiment`) and imported lazily inside one adapter function, so the API and offline code never import it.
- D-M5-7 Knowledge test: 10 four-option questions, each tied to one `CATALOG` item id, its `source_ids` and an `answer_evidence` substring of that item's text. Flat structured output `KnowledgeTestAnswers{q01..q10: str}` (M1 finding: no lists in structured output). Baseline = questions only; post = the scenario report's `checklist_markdown` (what a user downloads) plus the questions. Live only, 2 scenarios x 2 conditions = 4 model calls. Reported as "LLM in test scenarios", never as people.
- D-M5-8 One results file `backend/evaluation/results/evaluation-results.json` with `runs.offline` and `runs.live` (each run replaces only its own section). `docs/evaluation.md` is generated from it. Raw per-run live reports go to `.data/evaluation/` (git-ignored). The file ships in the Lambda asset because the build copies `backend/`.
- D-M5-9 Checklist completion is state on the record: `AssessmentRecord.checklist_completed: dict[str, datetime]` (item id -> completed at, default `{}` so old records parse). `POST /api/reports/{report_id}/checklist` with `{item_id, completed}` (POST, because CORS allows only GET and POST). Only ids from a backend twin of `frontend/src/lib/safety.ts` `renderablePlanItems` are accepted (complete: all plan items; needs_human_review: `verified_item_ids` only; otherwise none), else 404 `not_found`. DynamoDB keeps it in an optional `checklist_json` attribute, written only when non-empty, updated with `UpdateItem` + `attribute_exists(report_id)`; read-modify-write, last write wins (documented). The API role gains `dynamodb:UpdateItem` on the assessments table only; that needs a redeploy (user step).
- D-M5-10 `MetricsView` keeps every existing key and adds: `assessments_completed` (= records with status `complete`), `pct_recommendations_verified` (pooled verified items / plan items over records with a plan, 1 decimal, null with no items), `checklist{items_completed, items_available, reports_with_progress}`, `localized_guidance{served_in_requested_language, english_fallback, by_requested_language}` where "served" means `plan.language == plan.requested_language` (only English is supported, D6). All pre-seeded with 0. No user counts.
- D-M5-11 `GET /api/evaluation` returns the results JSON, or 404 `not_found` when the file is missing. Path from new setting `EVALUATION_RESULTS_PATH` (default: the packaged file).
- D-M5-12 New dashboard route `/impact` (nav "Impact"), with a fixed statement that HeatWise makes no health-outcome claims, honest zero states, and a separate "Synthetic evaluation results" panel with a mode label on every number.
