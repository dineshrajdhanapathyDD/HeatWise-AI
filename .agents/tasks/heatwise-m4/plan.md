## Design decisions (made here, record them in design.md §10 as D-M4-1..10)

- D-M4-1 Job model. `JobManager` keeps its public surface (`submit`, `get`, `shutdown`, constructor `JobManager(run_fn, store, max_workers, max_pending, max_retained)`) but delegates to a `JobRepository` (`InMemoryJobRepository` = today's lock-guarded dict, `DynamoDbJobRepository`) and a `JobDispatcher` (`ThreadDispatcher` = today's pool, `LambdaDispatcher` = boto3 `lambda.invoke(InvocationType="Event")`). One function `execute_job(job_id, repository, store, run_fn)` runs a job for both the thread pool and the worker Lambda. Why: Lambda freezes after the response and does not share memory, so state must live in DynamoDB and the ~41 s run must happen in a separate invocation; local dev and all 223 existing tests keep the thread path unchanged. The worker async config has `retry_attempts=0` and the worker moves the job `queued -> running` with a conditional update, so a duplicate delivery is a no-op instead of a second Bedrock run. A job left `queued`/`running` past `JOB_STALE_AFTER_SECONDS` (default 420 = worker timeout 300 + 120 margin) is reported `failed` with code `assessment_timed_out` (covers a worker killed by its timeout). The API contract (`JobView` fields, status codes, 429) is unchanged; on DynamoDB the `report` of a succeeded job is read from the assessment store by `report_id`.
- D-M4-2 Lambda adapter: Mangum 0.22.0. Pure Python, pip-installable into the zip asset, no layer ARN per region and no extra process; and it can be tested offline by passing an API Gateway v2 event to the handler. Lambda Web Adapter would need a published layer ARN and a uvicorn process, and is harder to test without AWS. `lifespan="off"` (the only lifespan work is the thread-pool shutdown, which Lambda mode does not have).
- D-M4-3 Front door: API Gateway HTTP API (v2), `$default` route to the API Lambda, no API Gateway CORS config (FastAPI's tested `CORSMiddleware` stays the single CORS source, origins from config). Why: stage throttling (rate 5 / burst 10 default) caps Bedrock spend, access logs to a CloudWatch log group, $0 at idle, and HTTP APIs do not use the account-level API Gateway CloudWatch role, so no `AWS::ApiGateway::Account` is synthesized (the RoadGuard-dev role is never touched). A Function URL has no throttling and no access logs; a RestApi brings the account-role problem.
- D-M4-4 Lambda architecture and packaging: arm64 (Graviton, about 20% cheaper per GB-s), runtime `python3.13` (same minor as the dev venv, 3.13.15). No Docker: `infrastructure/scripts/build_lambda_asset.py` runs `uv pip install --target infrastructure/build/lambda --python-platform aarch64-manylinux_2_28 --python-version 3.13 --only-binary :all: -r infrastructure/lambda-requirements.txt -c <constraints from the dev venv freeze>` and copies `backend/` without `tests/` and `__pycache__`. Checked during planning with `uv pip install --dry-run` (same flags, the 7 top-level pins): 53 packages resolve, all as aarch64/pure wheels, at exactly the dev-venv versions. manylinux_2_28 is safe because the python3.13 runtime is Amazon Linux 2023 (glibc 2.34). The script prints the unzipped size and fails above 250 MiB (262,144,000 bytes). One asset serves both functions (handlers `backend.lambda_api.handler`, `backend.lambda_worker.handler`).
- D-M4-5 DynamoDB keys. Assessments table: PK `report_id` (S) for get-by-id; GSI `by_location` (PK `location_key` S = `summaries.location_key(report)`, SK `created_at` S) for history-by-place; GSI `by_created` (PK `entity` S = `"assessment"`, SK `created_at`) for newest-first listing, paging and `all()`. Attributes `request_json` (community profile, place, days) and `report_json` are separate string attributes (Req 8.3: profile data apart from weather/report data), `duration_ms` as a string. `created_at` is written in one fixed format `%Y-%m-%dT%H:%M:%S.%fZ` (UTC) so string order = time order. Items over 380,000 bytes raise `ValueError` (limit 400 KB; stored reports are 43-60 KB today). Jobs table: PK `job_id`; sparse GSI `pending` (PK `pending_pk` = `"pending"` only while queued/running, SK `created_at`, KEYS_ONLY) so `count_pending` is one `Select=COUNT` query over non-stale jobs; TTL attribute `expires_at` (epoch, `JOB_TTL_DAYS` default 7). Both tables on-demand (PAY_PER_REQUEST), AWS-owned encryption, no PITR by default (listed as a user decision). The constant `entity` partition is fine at this volume; documented as the first thing to shard (by month) if volume grows.
- D-M4-6 Sessions (Req 8.1). `build_session_manager(settings, session_id)` returns `FileSessionManager(session_id, storage_dir=SESSION_DIR)` (default `.data/sessions`, git-ignored via `.data/`), `S3SessionManager(session_id, bucket=SESSION_BUCKET, prefix=SESSION_PREFIX, region_name=AWS_REGION)` (prefix default `sessions`), or `None` (`SESSION_STORAGE=none`). Only the coordinator Agent gets it (`agent_id="coordinator"`), only when `run(..., session_id=...)` is given. The API uses `session_id = job_id` (unique per assessment); the CLI gets `assess --session-id ID` to continue a conversation. Separation: the session holds the coordinator conversation (place, community-level indicators, compact step summaries); raw weather payloads stay inside the specialists and reach storage only in the report. No new request field, so `AssessmentRequest` keys stay `{place, forecast_days, profile}`.
- D-M4-7 Bedrock IAM, verified on 2026-11-03 from https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-amazon-nova-2-lite.html ("Geo inference details", Geo US): `us.amazon.nova-2-lite-v1:0` called from us-east-1 routes to us-east-1, us-east-2, us-west-2 (us-east-2 and us-west-2 sources: same three; us-west-1 source: those plus us-west-1). The worker role gets `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream` on `arn:aws:bedrock:us-east-1:<account>:inference-profile/us.amazon.nova-2-lite-v1:0` and `arn:aws:bedrock:{us-east-1,us-east-2,us-west-2}::foundation-model/amazon.nova-2-lite-v1:0`. The route table lives in `infrastructure/stacks/bedrock_routes.py` with the URL and check date; an unknown (profile, region) pair makes synth fail with a clear message instead of guessing. The API Lambda has no Bedrock or S3 permission.
- D-M4-8 Stacks: `HeatWiseData` (2 tables, sessions bucket), `HeatWiseApi` (2 functions, explicit roles, 3 log groups, HTTP API), optional `HeatWiseFrontend` only with `-c heatwise:frontend=true` (private S3 bucket with OAC + CloudFront, `/api/*` behavior to the HTTP API origin with caching disabled so the site and API share one origin and need no CORS change; SPA rewrite with a CloudFront Function, not distribution error responses, which would also rewrite API 404s). Explicit IAM statements, never `grant_read_write_data` (it adds batch/delete/describe actions not needed). Explicit `logs.LogGroup` per function and for access logs, retention 14 days (context). No VPC, no NAT, no provisioned or reserved concurrency (reserved concurrency can fail on new accounts with a low concurrency quota; listed as a user decision). Data removal policy `RETAIN` by default, `-c heatwise:removal=destroy` switches tables and bucket to `DESTROY` (no auto-delete custom resource).
- D-M4-9 AgentCore (Req 11.2): logic in `backend/agentcore_handler.py` (no AgentCore import, tested offline), thin `backend/agentcore_entry.py` with `BedrockAgentCoreApp` + `@app.entrypoint` like the workshop's `samples/05-deploy/main.py`. `bedrock-agentcore==1.25.2` is an optional extra (`agentcore`), installed in the dev venv only so the wrapper test runs; it is never in the Lambda asset. Not deployed.
- D-M4-10 Pins: Python `mangum==0.22.0` (runtime dep), `moto==5.2.5` (dev), `bedrock-agentcore==1.25.2` (extra); infra venv `aws-cdk-lib==2.275.0`, `constructs==10.8.1`, `pytest==9.2.0`; CDK CLI `npx --yes aws-cdk@2.1147.0` (latest on npm, built against aws-cdk-lib 2.275.0). aws-cdk-lib 2.275.0 requires `constructs>=10.5.0,<11`, so 10.8.1 fits.

## Decisions the user must make before deploying (carry into the final report)
1. API auth: the HTTP API is public and unauthenticated; anyone with the URL can start Bedrock runs (bounded by throttling and max pending jobs). Options: keep for a demo, IAM auth, a Cognito JWT authorizer, or the CloudFront-only origin.
2. Data removal policy: RETAIN (default) or DESTROY on `cdk destroy`.
3. Bedrock model access for Nova 2 Lite in all three destination regions, and the model id/profile.
4. Throttle limits, `API_MAX_PENDING_JOBS`, optional worker reserved concurrency, and an AWS Budget alarm.
5. Frontend hosting on CloudFront or local only; CORS origins.
6. Log retention (14 days) and DynamoDB PITR (off).
