## Design decisions (made here, record them in design.md §9 in item 19)

- **D-M3-1 Weather detail on the report.** The report today only carries weather values as `evidence` strings (the forecast date is inside a description), which cannot drive a forecast chart. Add three optional, additive fields to `PreparednessReport`: `current_conditions: CurrentConditions | None`, `forecast: ForecastResult | None`, `alerts: AlertsResult | None`, filled in `build_report` from the ledger-backed `WeatherIntelligenceResult`. Old stored JSON still parses (defaults `None`). This gives screen C real temperature, humidity, per-day max/min, `alerts.explanation` and `alerts.official_sources` (IMD for India).
- **D-M3-2 Assessments are jobs.** `POST /api/assessments` validates, creates an in-memory job, runs it on a `ThreadPoolExecutor` (`API_JOB_WORKERS`, default 2) and returns `202` with the job. `GET /api/assessments/{job_id}` polls. A new `HeatWiseCoordinator` is built per job (the coordinator keeps per-run state in `self._state`, so it must not be shared across threads). On success the record is saved to the store and the job holds `report_id` and the report. Jobs are in memory only (lost on restart); M4 replaces this with a Lambda-friendly queue, recorded in tasks.md.
- **D-M3-3 Offline agent mode.** Offline dev and the UI demo need scripted models, not Bedrock. Add `AGENT_MODE: bedrock | offline` (default `bedrock`). `offline` builds the coordinator with per-agent `ScriptedModel`s whose scripts are generated from the job's location and days (same scripts as `test_coordinator.py`), against the configured weather provider (use `WEATHER_PROVIDER=demo`). To avoid importing test code at runtime, move `ScriptedModel`/`tool_call`/`text` into `backend/agents/scripted.py` and turn `backend/tests/scripted_model.py` into a re-export, so every existing test import keeps working. `/api/health` reports `agent_mode`, and the UI shows "Demo data" and "Scripted agents" badges.
- **D-M3-4 Store.** `backend/session/store.py`: `AssessmentStore` ABC (`save`, `get`, `list`, `count`) and `JsonFileAssessmentStore(directory)`: one `<report_id>.json` per record, atomic write (temp file + `os.replace`), a `threading.Lock`, newest first by `created_at`. `ASSESSMENT_STORE_DIR` default `.data/assessments` (add `.data/` to `.gitignore`). A record holds only `report_id`, `created_at`, `duration_ms`, the request (`place`, `forecast_days`, community `profile`) and the report. No personal data: the request models use `extra="forbid"`, so a `name` or `phone` field is rejected with 422.
- **D-M3-5 Request shape and form mapping.** Request: `{"place": {"name", "district"?, "state"?}, "forecast_days": 1-7 (default 3), "profile": CommunityProfile fields}`. The backend composes `location = ", ".join([name, district, state] non-empty)`, which matches Open-Meteo geocoding (`open_meteo.py` searches the first part and prefers results whose admin fields contain every qualifier). Each part and the composed string go through `normalize_location`; days through `validate_forecast_days` (both in field validators, `mode="before"`).
  Form fields mapped onto `CommunityProfile`: population groups -> `elderly`, `young_children`, `pregnant_women`, `chronic_illness_group`, `outdoor_workers`, `farmers`; water availability (adequate / limited) -> `limited_water_access`; shade and cooling access (adequate / limited) -> `limited_shade_or_cooling`; terrain (plains / hilly / coastal / not sure) -> `terrain` (backend-meaningful, affects IMD rules and confidence, so it is added); preferred language -> `preferred_language` with an inline note that plans are English only for now; forecast days -> `forecast_days`.
  Left out, recorded in tasks.md as gaps: **community category** (no backend field), **outdoor exposure level** (no backend field; the "People who work outdoors" group is the real indicator), and a separate **city** field (geocoding takes one place name plus qualifiers, so the form has "City, town or village", "District", "State"). In demo mode the place fields are replaced by a select of `demo_locations` from `/api/health` (demo geocoding only accepts the exact keys).
- **D-M3-6 History changes and metrics in the backend.** `GET /api/history` returns summaries with `changes` against the previous stored report for the same location key (resolved `name|admin1|country` lowercased, else the query): risk category from/to, heat index delta, max forecast delta, indicators added/removed. `GET /api/metrics` counts stored records only: totals by status, risk category, data mode, plans generated, verification passed/failed/not_run, mean `pct_items_verified` and mean `duration_ms` (null when there is nothing to average). No user counts, no invented numbers.
- **D-M3-7 Error envelope.** Every error is `{"error": {"code", "message", "fields": [{"field", "message"}]}}`: `validation_error` 422 (pydantic `"Value error, "` prefix stripped), `not_found` 404, `too_many_jobs` 429 (more than `API_MAX_PENDING_JOBS`, default 20, queued/running), `http_<status>` for other HTTPExceptions, `internal_error` 500 with no stack trace. CORS: `API_CORS_ORIGINS` default `["http://localhost:5173", "http://127.0.0.1:5173"]`, methods GET/POST, header Content-Type. `npm run preview` also uses port 5173 (`--strictPort`) so the production build hits the same allowed origin.
- **D-M3-8 Frontend structure.** Vite + React 19 + TS + Tailwind v4 (`@tailwindcss/vite`, tokens in `@theme`), `react-router-dom` for real URLs (keyboard and back button work): `/` (A), `/assess` (B), `/assessments/:jobId` (job progress), `/reports/:reportId/{climate,risk,plan,activity}` (C-F under one `ReportLayout` that always renders the disclaimer and `report.notices`), `/history` (G). Landing (A) is built as the app's home screen under the app-screen run (not the marketing page run, which would demand a photo floor this tool does not have); record this in the report. Recharts draws the forecast (one hue on daily max, neutral for min, with a visually-hidden data table). Framer Motion only for the activity-step disclosure and the job status line, under `<MotionConfig reducedMotion="user">`; no entrances. Lucide icons at 16px, grey, only in nav and affordances.
- **D-M3-9 Safety rule in one function.** `src/lib/safety.ts` `renderablePlanItems(report)`: `complete` -> all `recommended_actions.items`; `needs_human_review` -> only items whose id is in `verification.verified_item_ids`; `incomplete` or no plan -> `[]`. The plan screen renders only this list, shows the "Not verified - needs human review" banner on `needs_human_review`, and downloads exactly `report.checklist_markdown` as a Blob (`heatwise-checklist-<report_id>.md`). Incomplete reports show `missing_information` and "No preparedness plan was built" and no download.
- **D-M3-10 Pinned versions** (checked with `npm view` today; peer ranges checked): react 19.3.1, react-dom 19.3.1, react-router-dom 7.18.5, framer-motion 14.9.0, recharts 3.10.1, lucide-react 1.66.0; dev: typescript 6.0.3 (typescript-eslint needs `<6.1.0`, so not 7.x), vite 8.3.5, @vitejs/plugin-react 6.2.1, tailwindcss 4.3.3, @tailwindcss/vite 4.3.3, vitest 5.0.5, jsdom 30.1.3, @testing-library/react 16.3.3, @testing-library/jest-dom 7.0.1, @testing-library/user-event 14.6.8, eslint 9.39.5 and @eslint/js 9.39.5 (eslint-plugin-jsx-a11y 6.10.2 does not support ESLint 10), typescript-eslint 8.72.1, eslint-plugin-react-hooks 7.1.1, eslint-plugin-react-refresh 0.5.7, eslint-plugin-jsx-a11y 6.10.2, globals 17.14.0, @types/react 19.3.0, @types/react-dom 19.3.0, @types/node 22.20.5.
